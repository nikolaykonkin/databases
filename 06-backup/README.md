# Database Backup: Strategies and Tools

Стратегии резервного копирования баз данных: полное, инкрементное, PITR. Практика на PostgreSQL (pg_dump/pg_restore) и MySQL (binlog). Разбор случаев, когда реплика выгоднее бэкапа.

## Задача 1. Сценарии резервного копирования

**Что требовалось.** Для финансовой компании описать варианты бэкапов в трех сценариях: восстановление за предыдущий день, восстановление за час до поломки, мгновенное переключение при отказе.

### 1.1. Восстановление данных за предыдущий день

Подходит **полное резервное копирование (full backup)**, выполняемое раз в сутки — например, ночью в период минимальной нагрузки.

- Снимается полный снапшот или дамп базы каждые 24 часа.
- Восстановление сводится к разворачиванию последнего полного бэкапа.
- **Плюсы:** простота реализации и восстановления, предсказуемое время recovery.
- **Минусы:** если нужна точка восстановления «ровно на конец предыдущего дня», важно снимать бэкап строго по расписанию (например, в 00:00). Иначе будут расхождения в несколько часов.

Для больших БД полный бэкап можно дополнить снапшотами диска (LVM, облачный диск) — это быстрее и не нагружает СУБД.

### 1.2. Восстановление данных за час до поломки

Точность на уровне часа — одного суточного бэкапа недостаточно. Нужна связка:

- **Полное резервное копирование** — базовая точка, раз в сутки или раз в неделю.
- **Инкрементное или дифференциальное резервное копирование** — каждые несколько часов.
- **Резервное копирование журналов транзакций (WAL / binlog)** — они пишутся непрерывно и позволяют восстановить состояние на любой момент времени (Point-In-Time Recovery, PITR).

Схема восстановления: разворачивается последний полный бэкап, накатываются инкременты, поверх — логи транзакций до нужной секунды. Это дает точность вплоть до конкретной транзакции.

### 1.3*. Мгновенное переключение при отказе

Такой сценарий возможен, но реализуется **не через бэкапы**, а через **репликацию и кластеризацию**:

- **Master-slave (primary-replica) репликация** — реплика в реальном времени получает изменения с мастера. При падении мастера реплика быстро повышается до основной роли.
- **Кластеры с автоматическим failover** — Patroni для PostgreSQL, Galera Cluster или Group Replication для MySQL, отказоустойчивые конфигурации в managed-сервисах облаков. Переключение происходит автоматически, за секунды.
- **Бэкапы остаются страховкой** на случай логических ошибок (удаление данных, повреждение), а репликация закрывает задачу мгновенного переключения при физическом отказе сервера.

Задачи бэкапа и высокой доступности решаются разными механизмами, которые дополняют друг друга.

## Задача 2. PostgreSQL: pg_dump и pg_restore

**Что требовалось.** Привести пример команды резервирования и восстановления БД из официальной документации. Описать автоматизацию.

### 2.1. Команды

Создание резервной копии в формате custom (сжатие + выборочное восстановление):

```bash
pg_dump -U postgres -h localhost -F c -d mydatabase -f mydatabase.dump
```

Восстановление:

```bash
pg_restore -U postgres -h localhost -d mydatabase -c mydatabase.dump
```

Расшифровка флагов:

- `-F c` — формат custom (сжатый архив вместо текста SQL).
- `-d` — имя целевой базы.
- `-c` — очистить (DROP) существующие объекты в базе перед восстановлением.

Резервное копирование всего кластера (все БД, роли, табличные пространства):

```bash
pg_dumpall -U postgres -f cluster_backup.sql
```

### 2.1*. Автоматизация

Да, процесс автоматизируется:

- **cron** — простейший вариант: скрипт с `pg_dump` запускается по расписанию (например, в 3:00 ночи), файлы именуются с датой (`mydatabase_$(date +%Y%m%d).dump`) и складываются в отдельное хранилище (S3, отдельный сервер).
- **WAL-archiving + PITR** — включение архивирования журналов упреждающей записи (`archive_mode = on`, `archive_command`) позволяет восстанавливать базу на любую секунду между полными бэкапами.
- **pgBackRest** и **Barman** — специализированные инструменты: полные, инкрементные и дифференциальные бэкапы, retention-политика, проверка целостности, PITR без ручной работы с WAL-файлами.
- **Managed-сервисы в облаках** (RDS, Cloud SQL) — автоматическое резервное копирование включается одной настройкой, без отдельных скриптов.

## Задача 3. MySQL: инкрементное копирование

**Что требовалось.** Привести пример команды инкрементного резервного копирования MySQL. Описать, когда реплика выгоднее бэкапа.

### 3.1. Инкрементное копирование через binlog

В MySQL инкрементное копирование реализуется через **бинарные логи (binary log)**, а не отдельной командой.

Порядок действий:

1. Включить бинарное логирование в конфигурации сервера (`log_bin = ON`).

2. Сделать полный бэкап с записью позиции binlog (точка отсчета):

```bash
mysqldump --single-transaction --master-data=2 -u root -p --all-databases > full_backup.sql
```

Флаг `--single-transaction` дает консистентный снимок InnoDB без блокировки таблиц, `--master-data=2` записывает в дамп позицию binlog в виде комментария.

3. Далее сохранять только новые binlog-файлы, накопившиеся с момента последнего бэкапа:

```bash
mysqladmin -u root -p flush-logs
cp /var/lib/mysql/mysql-bin.000123 /backup/incremental/
```

Путь к binlog зависит от ОС и способа установки. В Docker-контейнере это `/var/lib/mysql`, на macOS через Homebrew — `/opt/homebrew/var/mysql`.

4. Восстановление: сначала разворачивается полный бэкап, затем накатываются binlog-файлы через `mysqlbinlog`:

```bash
mysql -u root -p < full_backup.sql
mysqlbinlog mysql-bin.000123 mysql-bin.000124 | mysql -u root -p
```

`mysqlbinlog` поддерживает флаги `--start-datetime` и `--stop-datetime` для восстановления на конкретный момент времени (PITR).

### 3.1*. Когда реплика выгоднее бэкапа

Реплика (слейв, читающий поток изменений с мастера) дает преимущество в следующих случаях:

- **Минимальное время простоя (RTO близко к нулю)** — при отказе мастера реплику можно быстро повысить, тогда как восстановление из бэкапа занимает время на разворачивание дампа и накат логов.
- **Снятие нагрузки с продакшн-базы** — `mysqldump` может блокировать таблицы или создавать нагрузку на I/O; бэкап удобнее снимать именно с реплики.
- **Балансировка read-нагрузки** — реплика попутно используется для чтения (отчеты, аналитика), чего бэкап дать не может.
- **Аварийное восстановление в реальном времени** — реплика содержит актуальные данные, а бэкап — только состояние на момент снятия копии.

**Важно:** реплика не заменяет бэкап полностью. Она не защищает от логических ошибок (случайный `DROP TABLE` или `DELETE`), которые мгновенно реплицируются на слейв. На практике используют комбинацию: реплика — для высокой доступности и снятия нагрузки, регулярный бэкап (полный + инкрементный через binlog) — для защиты от логических ошибок и долгосрочного хранения.
